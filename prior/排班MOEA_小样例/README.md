# 排班 MOEA 小样例：机器人—工具排班上的场景化改进

2026-10-13。目标：在一个具体场景（机器人—工具值班排班）上，验证几项针对该场景的小改进是否有效，为"针对排班问题做算法小创新"这条路线提供依据。

## 问题从哪来

`roster_sim.py` 是 Python 重写的排班仿真，逻辑仿照：
- `算法库/目标函数/排班/problem.cpp` 中的 `robot_arrangement` / `robot_arrangement_moea`（C++ 原版，双目标）；
- `他人毕设/.../graduate_code_judge_double/Evaluate.py` 及 `view.md`（3 类机器人、4 类工具、多级维修的场景表）。

问题设定：
- **场景**：值班点必须始终且只有 1 台机器人值岗，连续覆盖 720 或 1440 小时。每班派 1 台机器人，携带固定数量的适配工具。机器人流程为：准备 → 安装 → 去程 → 值岗 → 收尾 → 返程 → 卸载，然后扣减各级维修剩余工时，再做多级维修判断（不需维修则充电）；工具流程为：卸载后保养。
- **编码**：随机键，长度为 2 × 最大班次数。前半段选机器人（复用已有或新开某类型），后半段选工具。
- **目标**：f1 = 机器人数 + 工具数；f2 = 均衡度（值岗次数、值岗时长、首次维修间隔三项标准差的加权和）。权重与 C++ 版相同。

**实例**（6 个）：维修级数 1/2/3 × 时长 720/1440，另加一个资源上限缩到 60% 的"紧"实例。随机解的可行率：宽松的 720 小时实例约 100%，1440 小时实例约 15%，"紧"实例约 2%。

## 比较的改进

| 改进 | 针对的场景结构 | 做法 |
|---|---|---|
| 阈值解码 | 原解码 `int(x·(可用机器人数+类型数))` 中，"复用还是新开"的含义随可用列表长度漂移，而且天然偏向新开机器人 | 基因 < θ（0.85）则复用，否则新开。复用/新开的决策与列表长度解耦 |
| 排序解码 | 复用哪台机器人原本按编号决定，与状态无关 | 在阈值解码基础上，可用机器人按出勤次数升序排列，基因越小越倾向派最闲的机器人 |
| 分级惩罚 | 原做法不可行一律返回 30000，搜索空间里出现大片平台 | 不可行解按"仿真推进到的时刻"分级 |
| 仿真感知变异 | 解码轨迹里可以看出问题出在哪个班次 | 父代不可行：把失败班次附近的基因改到复用区间。父代可行：要么把一次"新开"改成复用，要么让出勤最多的机器人让出一个班次 |
| 规则播种 | "每班都复用最闲的机器人"本身就是一条可行规则 | 在初始种群中放入全 0 基因（即该规则）及 9 个小扰动版本 |
| 分层精英（已放弃） | f1 是整数，前沿呈台阶状 | 每个 f1 取值各保留一个均衡度最好的解，并从中取父代。小规模试跑中在原解码下反而有害，未进入正式实验 |

骨架统一为 NSGA-II（SBX + 多项式变异，种群 100，100 代，即 1 万次评价）。所有变体都以"全部已评价可行解的非支配集"作为输出。HV 在每个实例内按全部运行统一归一化。

## 结果（6 实例 × 10 种子，详见 `results_v3_only.md`、`results_summary.md`）

**1. 逐步改进的 HV 对比**（`results_v3_only.md`）

| 实例 | 原解码(死罚) | 阈值解码+分级 | 排序解码+分级 | 排序+分级+仿真变异 |
|---|---|---|---|---|
| L1-720 | 0.43 | 0.78 | 0.86 | **0.95** |
| L2-720 | 0.66 | 0.94 | 0.96 | **1.00** |
| L3-720 | 0.61 | 0.81 | 0.84 | **0.98** |
| L3-720紧 | 0.53 | 0.94 | 0.94 | **1.01** |
| L1-1440 | 0.55 | 0.88 | 0.91 | **1.02** |
| L3-1440 | 0.67 | 0.97 | 1.01 | **1.12** |

完整方案在全部 6 个实例上都排第一，相对基线 p ≤ 0.006（配对 Wilcoxon，10 对）。

**2. 各步改进的单独贡献**（相邻两个变体之间的配对检验）

| 实例 | 阈值解码 vs 原解码 | 排序 vs 阈值 | 仿真变异 vs 无 |
|---|---|---|---|
| L1-720 | +0.35 (p=0.006) | +0.08 (0.22) | +0.09 (0.26) |
| L2-720 | +0.28 (0.008) | +0.02 (0.68) | +0.04 (0.54) |
| L3-720 | +0.20 (0.006) | +0.03 (0.54) | +0.14 (**0.014**) |
| L3-720紧 | +0.30 (0.006) | +0.00 (0.15) | +0.07 (0.053) |
| L1-1440 | +0.28 (0.006) | +0.03 (0.61) | +0.12 (0.13) |
| L3-1440 | +0.29 (0.008) | +0.04 (1.00) | +0.11 (**0.041**) |

- **阈值解码是主要贡献**，6 个实例上都显著。最少资源数从 31–41 降到 23–31。
- **仿真感知变异**在 6 个实例上都是正向，其中 2 个显著、1 个接近显著。
- **按出勤排序**是小幅正向，但都不显著。
- **分级惩罚**只在"紧"实例上有作用（0.53 → 0.64，不显著），因为其他实例上不可行解很少。

**3. 规则播种**（`results_summary.md`）

播种后找到的最少资源数从 21–30 降到 13–19。例如在 L1-1440 上找到了 13 个资源、均衡度 6.4 的解，而不播种时最好只有 28 个资源、均衡度 6.9。这说明原来的搜索漏掉了大片好解。

但播种后种群集中到低资源一端，前沿只覆盖约 3 个台阶，所以 HV 并没有全面提高（跨实例平均排名 1.33，不播种为 1.67）。

## 局限

- 这是 Python 简化重写，不是你的 C++ 原问题。工具解码、可用性判定等细节与原版有出入，结论需要回到 C++ 版本验证。
- 实例全部来自同一张参数表的变体，多样性有限。
- 只比了 NSGA-II 骨架；评价预算只有 1 万次。

## 下一步

1. **解决播种后的覆盖问题**：在新的解码下重试"按资源数分层的精英"，或者为每个资源数层保留一个解。原来设计它就是为了这个问题，只是在原解码下没用上。
2. **移植到 C++**：阈值解码只需改 `problem.cpp` 中 `int select_robot = (var[i] - 1e-3) * (available_robot_list.size() + task.objects_type["Robot"]);` 这一行及其后的分支。仿真感知变异需要让目标函数返回解码轨迹（失败班次、各班次派出的机器人）。
3. **扩充实例**：用毕设工程中的场景生成逻辑（`generate_double.py`，随机增删流程节点）生成更多实例，并检验结论是否稳定。
